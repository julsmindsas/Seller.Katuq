Onboarding DIAN por empresa — facturación electrónica directa

Cómo llevar una empresa cliente de cero a facturando electrónicamente con el motor DIAN de Katuq (modo de operación software propio, desarrollo tecnológico adquirido — Res. 000165/2023, art. 28). El principio rector: el cliente solo hace lo que legalmente es indelegable; todo lo demás es nuestro. Guía espejo para el cliente: manual-cliente.html.

Contenido 1. Pipeline de onboarding 2. Sesión acompañada DIAN 3. Paquete de activación 4. Configuración en Katuq 5. Set de pruebas 6. Checklist go-live 7. Operación y monitoreo 8. Troubleshooting 9. URLs y referencias

1 · Pipeline de onboarding (quién hace qué, en orden)

Cliente
F1 — RUT con responsabilidad 52 Verificar casilla 53. Si falta, actualizar RUT en MUISCA. Bloqueante para todo lo demás.
Cliente
F2 — Certificado de firma digital (.p12) Persona jurídica, para facturación electrónica, en software (no token físico). CA acreditada ONAC: Certicámara, GSE, Andes SCD. Corre en paralelo con F3.
Ambos
F3 — Sesión acompañada: registro en portal de habilitación DIAN Videollamada de 30 min. El cliente entra (token al correo del RUT), nosotros dictamos. Salida: Software ID + PIN + TestSetId. Ver sección 2.
Katuq
F4 — Set de pruebas en ambiente de habilitación Enviar el set completo (facturas + notas C/D) al WS de habilitación hasta estado Aceptado. Ver sección 5.
Cliente
F5 — Resolución de numeración en MUISCA Prefijo + rango + vigencia. Recomendarles rango ≥ 50.000 y vigencia 24 meses. Puede correr en paralelo con F4.
Cliente
F6 — Entrega del paquete de activación Certificado + contraseña + resolución + datos fiscales, SOLO por canal seguro. Ver sección 3.
Katuq
F7 — Configuración, asociación en producción y go-live integration_configs/secrets, registro del rango en portal FE de producción (clave técnica), primera factura real acompañada. Ver secciones 4 y 6.
💡 Tiempos reales esperados RUT al día → 1-2 semanas end-to-end. El camino crítico es certificado (1-3 días) + set de pruebas (2-5 días). Los pasos del cliente suman < 2 horas de su tiempo.

2 · Sesión acompañada DIAN (guion de la videollamada)

Objetivo: salir de la llamada con Software ID, PIN y TestSetId anotados. Duración: ~30 min.

  1. Antes de la llamada: confirmar que el cliente tiene a mano NIT, cédula del representante legal y acceso al correo registrado en el RUT. Definir el PIN que vamos a usar (numérico, lo genera Katuq y queda registrado en el vault del tenant).
  2. Cliente entra a HAB catalogo-vpfe-hab.dian.gov.co → ingreso Empresa (NIT + cédula rep. legal).
  3. DIAN envía token al correo del RUT → el cliente lo abre y comparte pantalla.
  4. Menú Registro y habilitación → registrarse como Facturador electrónico (si no aparece, verificar responsabilidad 52 — F1 incompleta).
  5. Asociar modo de operación → Software propio: nombre del software = Katuq, PIN = el acordado.
  6. La DIAN muestra el Identificador de Software (UUID) y crea el set de pruebas con su TestSetId. Copiar AMBOS al vault del tenant en ese momento (no a chat, no a correo).
  7. Cerrar la llamada explicándole F5 (numeración) y F6 (paquete de activación) con el manual del cliente en pantalla.
⚠️ Cliente que ya factura con otro proveedor/software El registro como facturador ya existe: solo se agrega un modo de operación "Software propio" nuevo (Katuq) sin tocar el vigente. Coordinar fecha de corte: el otro software sigue emitiendo hasta que el nuestro pase a producción, y la numeración nueva arranca ese día. Nunca dos softwares emitiendo sobre el mismo rango.

🔒 Reglas duras de manejo
  • Certificados y contraseñas NUNCA por WhatsApp, correo o chat — solo el canal seguro de onboarding.
  • Nada de secretos hardcodeados ni en integration_configs — los secretos viven en integration_secrets (mismo patrón que Shopify/WO/SIIGO).
  • Canónica de integraciones en INGLÉS: integrations.dian (Artículo XV v2 de la constitución de specs).
  • Registrar fecha de vencimiento del certificado al guardarlo — alimenta el monitoreo de la sección 7.

4 · Configuración en Katuq

El motor DIAN es una estrategia más del AccountingManager (services/accounting/providers/dianProvider.js), igual que SIIGO y World Office. Config por empresa vía IntegrationConfigService.

Estructura de configuración del tenant

integration_configs / {companyId} / dian
{
  "enabled": true,
  "environment": "habilitacion" | "produccion",
  "softwareName": "Katuq",
  "testSetId": "...",                  // solo habilitación
  "numbering": {
    "resolutionNumber": "18760000001",
    "prefix": "FEKQ",
    "from": 1,
    "to": 50000,
    "current": 1,                      // consecutivo — SOLO se avanza en transacción Firestore
    "validFrom": "2026-07-01",
    "validTo": "2028-07-01"
  },
  "issuer": {
    "businessName": "...", "nit": "...", "dv": "...",
    "address": "...", "municipalityCode": "05001",   // código DANE
    "taxRegime": "...", "responsibilities": ["O-13", "..."], "ciiu": "..."
  },
  "receiptEmailCopy": "facturas@cliente.com"
}

integration_secrets / {companyId} / dian
{
  "certificateP12Base64": "...",
  "certificatePassword": "...",
  "certificateExpiresAt": "2027-07-01",
  "softwareId": "uuid-dian",
  "softwarePin": "...",
  "technicalKey": "..."                // clave técnica del rango (producción)
}
⚠️ Consecutivos = transacción Firestore SIEMPRE El número de factura se toma y avanza dentro de una transacción (mismo criterio que inventario). Un consecutivo repetido o saltado frente al rango autorizado = rechazo DIAN y dolor de cabeza contable.

Activación del flujo de venta

  • En la empresa: generarFacturaElectronica = true y proveedor de facturación = dian.
  • El flujo es el mismo de SIIGO/WO: crear-ventas dispara la facturación al aprobarse el pago; el manager delega en la estrategia dian.

5 · Set de pruebas de habilitación (F4)

Con Software ID + PIN + TestSetId y el certificado del cliente, se corre el set contra el ambiente de habilitación HAB. El set exige enviar documentos válidos de cada tipo (facturas de venta, notas crédito, notas débito) hasta que el portal marque el set como Aceptado.

  1. Configurar el tenant con environment: "habilitacion".
  2. Ejecutar el script de set de pruebas (envía vía SendTestSetAsync y consulta estado con GetStatus por trackId).
  3. Revisar cada documento: los rechazos traen las reglas violadas (códigos de regla del anexo técnico) — corregir datos del emisor/documento y reenviar.
  4. Verificar en el portal de habilitación que el set quedó Aceptado.
  5. El cliente (en 2 minutos, o en la misma sesión si ya tiene numeración) asocia el modo de operación en PROD catalogo-vpfe.dian.gov.co, donde se registra/sincroniza el rango de numeración y obtenemos la clave técnica.
💡 Los documentos de prueba no son reales Todo lo del ambiente de habilitación es de mentira (sin efectos fiscales). Se pueden usar datos del emisor reales con adquirientes ficticios del anexo (consumidor final 222222222222).

6 · Checklist go-live (clic para marcar — se guarda por navegador)

Duplicar esta lista en el ticket del tenant. No se activa producción con un solo ítem sin chequear.

  • RUT del cliente con responsabilidad 52 verificado (pantallazo en el ticket)
  • Certificado .p12 cargado en integration_secrets, contraseña probada (firma de prueba OK) y vencimiento registrado
  • Software ID + PIN en el vault; set de pruebas Aceptado en portal HAB
  • Resolución de numeración vigente cargada; prefijo/rango/fechas coinciden con el PDF de MUISCA
  • Rango asociado en portal PROD y clave técnica guardada en integration_secrets
  • Datos fiscales del emisor validados contra el RUT (dirección y municipio DANE exactos — causa #1 de rechazo)
  • environment: "produccion" y generarFacturaElectronica: true en la empresa
  • Primera factura real emitida en sesión acompañada: validada por DIAN (CUFE OK), PDF con QR correcto, email al adquiriente recibido
  • Nota crédito de prueba real sobre esa factura (anulación) emitida y validada
  • Monitoreo activo: alertas de consumo de numeración y vencimientos (sección 7)
  • Cliente confirmó recepción de la copia de facturas en su correo fiscal

7 · Operación y monitoreo continuo

  • Estados por documento: cada emisión guarda trackId, CUFE, estado DIAN y XML en la colección de auditoría del motor (nunca console.log). Los rechazos disparan reintento con backoff y alerta si persisten.
  • Numeración: alerta al 80% de consumo del rango o a 60 días del vencimiento de la resolución — se le pide al cliente renovar en MUISCA (mismo trámite F5).
  • Certificados: alerta a 45 y 15 días del vencimiento. Sin certificado vigente NO se factura: es el bloqueo duro más común.
  • Contingencia: si la DIAN está caída, los documentos quedan en cola con reintento; no se entrega factura al cliente final sin validación DIAN (modelo de validación previa).
  • Cambios normativos: los anexos técnicos cambian (p. ej. Res. 000202/2025 aplica en 2026). Suscribirse al micrositio DIAN y revisar trimestralmente.

8 · Troubleshooting — rechazos y errores frecuentes

SíntomaCausa típicaAcción
Rechazo por datos del emisor (dirección/municipio) Dirección o código DANE no coincide exactamente con el RUT Copiar textual del RUT (casillas 38-41). Corregir issuer y reemitir.
Rechazo por numeración Consecutivo fuera de rango, resolución vencida o clave técnica errada Validar numbering vs PDF de MUISCA y clave técnica del portal PROD.
Error de firma / política de firma Certificado vencido, contraseña mala o cadena de confianza incompleta Probar el .p12 con firma local; verificar vencimiento; si venció → cliente reexpide con la CA.
CUFE inválido Diferencia entre los valores del XML y los usados para el hash (totales, fechas, clave técnica) Bug del motor: comparar la cadena de concatenación contra el anexo técnico. Escalar a dev.
El set de pruebas no avanza Documentos aceptados con notificación pero set incompleto (faltan tipos de documento) Revisar en portal HAB qué tipos faltan (notas C/D suelen olvidarse) y enviarlos.
Timeout / caída del WS DIAN Ventanas de mantenimiento DIAN (frecuentes de madrugada) o picos La cola reintenta sola. Si es masivo, revisar estado de servicios en el micrositio DIAN antes de tocar nada.
Cliente no recibe el token de acceso al portal Correo del RUT desactualizado o buzón lleno Actualizar correo en el RUT (MUISCA) primero; reintentar al día siguiente.

⚠️ Marco legal del modelo — leer antes de vender esto Operamos como software propio del cliente ("desarrollo tecnológico adquirido", Res. 000165/2023 art. 28): cada empresa se habilita ante la DIAN con el software de Katuq registrado a su nombre y firma con SU certificado. Katuq NO está habilitado como Proveedor Tecnológico (art. 616-4 E.T.) — no podemos ofrecer "nosotros facturamos por ti ante la DIAN" como servicio; el habilitado y responsable ante la DIAN es siempre el cliente. Si el volumen de tenants lo justifica, evaluar habilitación formal como PT o proveedor marca blanca (Factus u otro) — decisión abierta, ver CONTRACT.md.
